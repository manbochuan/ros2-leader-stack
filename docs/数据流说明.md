# 数据流说明 —— 用户的一句话是怎么被处理的

> 回答一个常见困惑：**用户输入是直接给 Leader 服务的吗？**
> **不是。** 中间要过「百炼主 agent」和「插件」两跳，而且**只有代码层模式才会走到 Leader**。

## 二、两种模式，数据流不同

### 模式 A：提示词层（现在用的）

```
学生 → 百炼主 agent
         ↓ 它自己判断该走哪条路（读提示词第 1/2/3/4 条）
         ├── ROS2 代码/项目 → 调百炼工作流（不过服务器）
         ├── 概念/报错/闲聊 → 自己答
         └── 其他领域       → 调插件 → 网关 ask_platform → 平台搭档
         
★ Leader 服务（:9200）完全不在链路上
```

### 模式 B：代码层（Leader 已写好，未启用）

```
学生 → 百炼主 agent
         ↓ 提示词里只写一句"交给 leader_orchestrate"，不做判断
         ↓ 调插件
       Leader 服务（:9200）
         ↓ 规则表分类（判断在代码里，确定）
         ├── 概念/报错/闲聊 → 自己答（调百炼小模型）
         ├── ROS2 需求      → 调 Partner ①②③
         └── 其他领域       → 调网关 ask_platform → 平台搭档
         
★ 这里有两层判断：主 agent 那一层（提示词）+ Leader 那一层（代码）
```

> **💡 关键：如果要做到 100% 确定，主 agent 那层的判断也要"消掉"** ——
> 提示词里写死"所有请求都交给 `leader_orchestrate`"，让它不做任何判断。
> 这样判断就只剩 Leader 里的规则表（代码）。

## 三、"用户输入是直接给 Leader 吗？"

**不是。要过两跳：**

| 跳 | 谁 | 做什么 | 在哪 |
|---|---|---|---|
| **1** | **百炼主 agent** | 读提示词，判断该不该交给 Leader | 阿里云百炼 |
| **2** | **插件** | 用 HTTP 转发给 Leader（带 `X-Auth-Token`） | 百炼侧配置 |
| **3** | **Leader 服务** | 分类 + 调度 | 你的服务器 9200 |

**而且：**

- **提示词层模式下，Leader 根本不在链路上**
- **只有代码层模式（提示词里写"交给 leader_orchestrate"）才会到达 Leader**
- **用户**永远只面对百炼主 agent** —— Leader 是它调用的一个后台服务，用户看不见**

## 四、各组件在哪、谁调谁

| 组件 | 跑在哪 | 端口 | 被谁调 |
|---|---|---|---|
| **百炼主 agent** | 阿里云百炼 | — | 学生（对话框） |
| **插件** | 百炼侧配置 | — | 主 agent |
| **Leader 服务** | 你的服务器 | 9200 | 主 agent（经插件） |
| **网关** | 你的服务器 | 9100 | Leader / 主 agent（经插件） |
| **acps-agent** | 你的服务器 | 8443 | **梧桐平台**（别人调我们） |
| **bailian-shim** | 你的服务器 | 9099 | acps-agent |
| **amp-forwarder** | 你的服务器 | — | 定时任务（心跳） |
| **百炼工作流 ①②③** | 阿里云百炼 | — | Leader（直连 DashScope API） |
| **平台上的其他搭档** | 各参赛者自己的服务器 | 各自 | 网关（经 AIP + mTLS） |

## 五、两种调用的机制完全不同（容易混）

| 调用 | 目标怎么定 | 走什么协议 | 需要什么 |
|---|---|---|---|
| **Leader → Partner ①②③** | **写死在配置里**（`PARTNER1_APP=...`） | **DashScope App Completion API**（HTTP + API Key） | 百炼 API Key |
| **Leader/主 agent → 网关 → 平台搭档** | **动态检索**（按 `need` 语义匹配） | **AIP + mTLS** | 客户端证书（私钥不出服务器） |
| **梧桐平台 → 我们** | 平台按 AIC 路由 | **AIP + mTLS** | 服务端证书（我们的 `server.pem`） |

**一句话：**
- **调百炼工作流** = 调自己的后端（写死 appId，用 API Key）
- **调平台搭档** = 调别人（动态检索，用 mTLS 证书）
- **被平台调** = 别人调我们（我们的智能体挂着，用服务端证书）

## 六、一次"项目需求"的完整数据流（假想是代码层模式）

```
① 学生：帮我做一个避障小车
      ↓
② 百炼主 agent：读提示词 → "交给 leader_orchestrate"
      ↓ 插件 HTTP POST http://YOUR_HOST:9200/leader
        {"text":"帮我做一个避障小车"}
      ↓
③ Leader：规则表命中"项目需求"
      ↓ HTTP 到百炼（DashScope API）
      Partner ①「需求分析」  → 约 10 秒 → 返回结构化需求 JSON
      ↓ 
      Leader 检查：① 认了、有具体问题 → 继续
      ↓ HTTP 到百炼
      Partner ②「项目规划」  → 用 requirement_json → 返回规划书 + 节点清单
      ↓
      Leader：并发 HTTP 到百炼
      Partner ③「代码生成」× N（每个节点一次）
      ↓
      Leader：汇总渲染（规划书用本地模板 + 学习指南 + 代码）
      ↓ 返回 {"reply": "...", "session_id": "s-xxx", "nodes": [...]}
④ 插件 → 主 agent → 学生看到完整结果
```

## 七、一次"调平台搭档"的完整数据流（两种模式都一样）

```
① 学生：推荐几个北京好吃的
      ↓
② 主 agent（提示词层）or Leader（代码层）：判断"不是 ROS2 领域"
      ↓ 插件 HTTP
      网关 POST /ask_platform  {"need":"推荐北京美食","input":"..."}
      ↓
③ 网关：
      · 跑 acps-cli discover query "推荐北京美食" → 拿到候选列表（含契约）
      · 按相关度依次尝试（失败自动试下一个，总预算 90 秒）
      · 按对方 ACS 的 inputModes 决定发文本还是 JSON
      · 用客户端证书 mTLS 连过去 → AIP start → 轮询 get → 取产物 → complete
      ↓
④ 平台上的「北京美食推荐智能体」处理 → 返回内容
      ↓
      网关 → 插件 → 主 agent/Leader → 学生
```

## 八、最容易混的三个点

| 困惑 | 答案 |
|---|---|
| **"用户输入直接给 Leader 吗？"** | ❌ 不是。要过「主 agent → 插件」两跳；提示词层模式下根本不到 Leader |
| **"Leader 是主 agent 吗？"** | 从**角色**上说，Leader 就是主 agent 的职责；从**实现**上说，我们把角色拆成了"百炼外壳 + 服务器内核" |
| **"调我们自己的智能体，走 `ask_platform` 还是 `/wf/*`？"** | 两条都能走：`/wf/*` 直连（快、超时 180 秒）；`ask_platform` 走平台检索（多一跳，但验证了"通过平台调自己家"） |
